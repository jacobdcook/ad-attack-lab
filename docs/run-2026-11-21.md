# Live run — 2026-11-21

First real run of the lab. DC01 built from the Windows Server 2022 eval ISO
(Standard Core, build 20348) on KVM, on an isolated host-only libvirt network
(`adlab`, 10.0.0.0/24, no LAN bridge). Setup pulled Sysmon over a temporary NAT
NIC that was detached before the attacks. No WS01 — the credential-access chain
runs against the DC alone.

Attacker = the Linux host (impacket + netexec + samba `net`).

## Notes

- 4768/4769/4662 only appeared after the audit policy was enabled, and 4662
  needed the replication-rights SACL on the domain head. Both are now in
  `setup-domain.ps1` (`Enable-Logging`). Before the fix the DC wrote none of them.
- The deliberately weak passwords (`password1`, `qwertyuiop`) were rejected by
  the default domain password policy, so jsmith (the AS-REP target) and bchen
  had no hash. `setup-domain.ps1` now turns complexity off before creating users.
- Kerberoast rule did not fire: a two-SPN domain never reaches `count > 5`. The
  RC4 4769 events are real; the threshold is the gap. Lower it or drop the count
  for a lab this size.
- LSASS was exercised with a controlled `OpenProcess(0x1010)`, not a real
  credential dumper (no WS01, no mimikatz on the DC). Sysmon also logged
  Defender (`MsMpEng.exe`) touching lsass with `0x101000` and `0x1000`. The Sigma
  rule's exact-match mask list skips those. The Wazuh rule 100150 as first
  written did not: its unanchored regex matched `0x101000`. Logtest caught it and
  the rule is now anchored (see the logtest doc). A dumper using another mask
  still slips past both.
